### 1. DeepSeek 开源 DSpark 投机解码框架，加速 DeepSeek-V4 生成速度 60-85%

**背景**：投机解码（Speculative Decoding）是一种不改变模型本身、通过“小模型草稿 + 大模型验证”来加速推理的技术。它把生成拆成两步：一个小型草稿模型快速提议一批 token，完整的目标模型再一次性验证这批 token。由于拒绝采样精确保持目标分布，质量无损。

**原来的问题**：已有的草稿模块存在权衡——自回归草稿（如 Eagle3）接受率高但草稿成本随块大小增长；并行草稿（如 DFlash）成本低但每个位置忽略邻居，导致“多模态冲突”和接受率衰减。

**这次发生了什么**：DeepSeek 开源了 DSpark 投机解码框架，并发布了配套的 DeepSpec 训练代码库（MIT 许可证）。DSpark 不是新模型，而是在 DeepSeek-V4 权重上附加一个草稿模块，通过“并行骨干 + 轻量级顺序头”的两阶段设计，同时拉动三个杠杆：更快草稿、更好草稿、更智能验证。

**具体变化**：
- 生产环境下，DeepSeek-V4-Flash 每用户生成速度比 MTP-1 基线提升 **60–85%**，V4-Pro 提升 **57–78%**。
- 离线测试中，接受长度比 Eagle3 高 **26–31%**，比 DFlash 高 **16–18%**。
- 一个置信度头和负载感知调度器在 GPU 空闲时验证更多 token，在繁忙时验证更少。

**为什么重要**：对使用 DeepSeek-V4 API 做产品的团队来说，这是立即可用的性能提升——不换模型就能加速，且代码和权重都已开源。原文来源为 AIHOT Featured，属于**待验证**信息，建议自行测试验证效果。

**建议动作**：如果你正在使用 DeepSeek-V4 的 API 或自部署推理，可以关注 DSpark 的集成方式，评估能否直接降低推理延迟和成本。

[11. DeepSeek 开源 DSpark 投机解码框架，加速 DeepSeek-V4 生成速度 60-85%](https://aihot.virxact.com/items/cmqwm45f901n6sly0gpl6b6l5)

### 2. 新浪开源 VibeThinker-3B：推理可压缩，事实知识不能

**背景**：新浪（微博母公司）发布了一款仅 3B 参数的小模型 VibeThinker-3B，基于阿里 Qwen2.5-Coder-3B 进行多阶段后训练（SFT → 强化学习 → 自蒸馏）。这不是一个通用大模型，而是一个实验性项目，旨在探究“小模型能否达到顶级性能”。

**具体变化**：
- 在 AIME26 等数学编程基准上，VibeThinker-3B 持平 DeepSeek V3.2、Kimi K2.5 等大 200–333 倍的模型。
- LiveCodeBench 超越所有 20B 以下模型。
- LeetCode 竞赛（训练结束后参加）解决 123/128 题，超过 GPT-5.2、Kimi K2.5、Claude Opus 4.6。
- 但在知识密集型基准 GPQA-Diamond 上大幅落后。

**为什么重要**：研究提出“参数压缩-覆盖假说”——逻辑推理依赖少数可压缩模式，而广泛世界知识仍需大参数。这对做推理应用的团队是个信号：如果你只需要数学/编程推理能力，小模型可能就够用，成本大幅降低。原文来源为 AIHOT Featured，属于**待验证**信息。

**建议动作**：如果你的应用场景以数学、编程、结构化推理为主，可以评估 VibeThinker-3B 是否满足需求，并关注其开源权重。

### 3. 我们构建了一个路由层来削减 AI 成本，结果搞砸了产品

**背景**：一个团队构建了 AI 推理路由层（routing layer），将部分请求路由到更便宜的模型，目标是削减 60% 的推理成本。

**结果**：便宜模型的质量损失在数月内未被发现，导致客户满意度下降和流失，最终损失是节省成本的 **4–5 倍**。

**为什么重要**：这是一个典型的“成本优化陷阱”——路由层看似聪明，但质量监控缺失会带来更大的隐性成本。原文来源为 BestBlogs AI High Score，属于**待验证**信息，但教训值得所有做 AI 产品的团队警惕。

**建议动作**：如果你正在使用或计划使用模型路由策略，务必建立持续的质量监控和 A/B 测试机制，不要只盯着成本数字。

## Agent / 编程工具趋势

### 1. Ornith-1.0：基于 Gemma 4 和 Qwen 3.5 的自脚手架编码 Agent 模型，开源权重

**背景**：Ornith-1.0 是 DeepReinforce 发布的首个模型，采用 MIT 许可证开源权重。它基于预训练的 Gemma 4（Apache 2.0 许可证）和 Qwen 3.5（Apache 2.0 许可证）构建，提供 9B Dense、31B Dense、35B MoE 和 397B MoE 四个变体。

**原来的问题**：开源编码 Agent 模型在工具调用和长链推理上往往不如闭源模型。

**这次发生了什么**：Ornith-1.0 在编码基准上达到开源模型 SOTA（state-of-the-art）。Simon Willison 使用 35B Q4_K_M GGUF（20GB）在 LM Studio 中测试，成功完成多项编码任务，包括查找代码、绘制图像，推理速度达 **103 tokens/sec**。

**具体变化**：模型能够熟练地运行 Agent 框架（agent harness）进行多次工具调用。测试中，它轻松处理了“查找 actor cookie 解码代码”和“查找按钮点击时打开插入对话框的代码”等任务。

**为什么重要**：这展示了开源编码 Agent 的新进展，可能影响开发者工具链的选择。作者的实际体验表明其具备实用能力。但需要注意，这是**技术社区**的个人测试，结果可能受测试条件和硬件环境影响。

**建议动作**：如果你在寻找本地可运行的编码 Agent 模型，可以下载 Ornith-1.0 的 GGUF 版本在 LM Studio 或 Ollama 中测试，评估其在你的工作流中的表现。

[1. Ornith-1.0 发布：基于 Gemma 4 和 Qwen 3.5 的自脚手架编码Agent模型，开源权重](https://simonwillison.net/2026/Jun/29/ornith)

5. **继续观察**：GLM 5.2 在安全基准上的表现、韩国芯片产能扩张对 HBM 价格的影响、Google 限制 Meta 使用 Gemini 的后续发展。
