### 生产级 AI Agent 迁移至 GPT-5.6：速度提升 2.2 倍，成本降低 27%

Ploy 团队分享了将生产级 AI Agent 从 Claude Opus 迁移至 GPT-5.6 Sol 的实测结果。Ploy 的 Agent 负责构建和编辑真实营销网站，需要规划页面、读取代码库、编写组件、生成图片并截图自检，对模型质量要求极高。在四个月里 Claude Opus 一直占据默认位置，GPT-5.6 是首个击败它的模型。迁移后，推理速度提升 2.2 倍，成本降低 27%，且完成工作质量持平甚至优于原模型。文章还详细分享了迁移过程中发现的关键调整和注意事项，包括模型行为差异、缓存策略变化等。**为什么重要**：该结果直接展示了 GPT-5.6 在生产 Agent 中的实际收益，对 Agent 工作流优化和模型选型有重要参考价值。**建议动作**：如果你的 Agent 工作流依赖 Claude Opus，建议在非生产环境中测试 GPT-5.6 的迁移效果，重点关注缓存策略和系统提示的适配。[7. 生产级AI Agent迁移至GPT-5.6：速度提升2.2倍，成本降低27%](https://ploy.ai/blog/migrating-a-production-ai-agent-to-gpt-5-6)

### vLLM v0.25.0 发布：模型运行器 V2 默认启用，PagedAttention 移除，Transformers 后端性能持平原生

vLLM 是一个高性能大模型推理服务框架，广泛应用于 AI 推理基础设施。本次 v0.25.0 版本包含 558 次提交，主要变化包括：
- **模型运行器 V2（MRv2）** 成为所有稠密模型的默认执行路径，并新增对 EVS、实时 embeddings、Mamba 混合模型前缀缓存、多模态前缀双向注意力、动态推测解码等支持。
- **旧版 PagedAttention 实现被移除**，V1/MRv2 后端已成为标准路径。
- **Transformers 建模后端性能达到与原生 vLLM 持平**，并新增 FP8 MoE 支持、CUDA graph 修复等。
- **新增模型支持**：LLaVA-OneVision-2、Unlimited OCR、GLM-5/DeepSeek-V3.2、MiniMax-M3 等。

**为什么重要**：vLLM 是 AI 推理基础设施的关键组件，本次更新直接影响部署性能、模型兼容性和开发者工作流。**建议动作**：如果你在生产环境中使用 vLLM，建议在测试环境中评估 v0.25.0 的兼容性和性能提升，特别是 MRv2 默认启用和 Transformers 后端性能提升。[1. vLLM v0.25.0 发布：模型运行器 V2 默认启用，PagedAttention 移除，Transformers 后端性能持平原生](https://github.com/vllm-project/vllm/releases/tag/v0.25.0)

### xAI Grok Build CLI 被曝默认上传整个仓库及 git 历史，关闭设置无效

社区分析显示，xAI 官方 Grok Build 编码 CLI（版本 0.2.93）在用户登录后，会向 xAI 发送三类数据：一是它读取的文件内容（包括 .env 密钥文件）以明文形式传输；二是整个仓库的全部文件内容及 git 历史，独立于 AI 智能体实际读取的文件——即使提示“不要读取任何文件”，Grok 仍将整个仓库作为 git bundle 上传至 Google Cloud Storage；三是该上传机制默认开启，且关闭“改进模型”设置无法禁用。在 12 GB 仓库测试中，/v1/storage 传输了 5.10 GiB 数据，而模型对话通道仅传输 192 KB，比例约 27,800 倍。分析未证明 xAI 使用这些数据进行训练，但证实了数据被传输、接收并存储。**为什么重要**：该问题直接影响使用 Grok Build 的开发者数据安全，可能泄露整个代码库和敏感信息，且用户无法通过设置阻止。**建议动作**：如果你使用 Grok Build，建议立即停止使用并检查是否有敏感信息被上传；关注 xAI 的官方回应和修复。[10. xAI Grok Build CLI 被曝默认上传整个仓库及 git 历史，关闭设置无效](https://aihot.virxact.com/items/cmrhagju201pqbir7t0tnsgfy)

### llama.cpp b9977：修复 Anthropic→OpenAI 转换中工具结果图片块丢失问题

llama.cpp 是一个在本地运行大模型的开源工具，支持多种硬件后端。本次 b9977 版本修复了 server 中 Anthropic→OpenAI 转换函数丢弃 tool_result 内图片块的问题。现在图片块会被正确转换为多模态内容部分，纯文本结果保持向后兼容。**为什么重要**：对于使用 llama.cpp server 并依赖多模态工具输出的用户，此修复确保模型能正确接收图片结果，避免功能异常。**建议动作**：如果你使用 llama.cpp server 且涉及多模态工具输出，建议升级到 b9977。[15. llama.cpp b9977：修复 Anthropic→OpenAI 转换中工具结果图片块丢失问题](https://github.com/ggml-org/llama.cpp/releases/tag/b9977)

### Mesh LLM 开源发布：通过 iroh P2P 网络池化多机 GPU 实现分布式推理，兼容 OpenAI API

Mesh LLM 是一个开源项目，能将多台机器上的 GPU 和内存池化，对外暴露兼容 OpenAI 的 API。它通过 iroh 网络库实现点对点连接，无需中央服务器。请求可在本地 GPU 运行、路由到已加载模型的节点，或将大模型按层分区（内部称“Skippy”）流水线式拆分到多台机器。系统内置 40 多个模型，从 5 亿参数到 235B MoE 巨模型均可支持。软件体积约 18 MB，启动后以 localhost:9337/v1 提供服务。**为什么重要**：Mesh LLM 为本地多机推理提供了一种去中心化、低门槛的解决方案，对 AI 基础设施和边缘部署有潜在影响。**建议动作**：如果你有多台 GPU 机器且希望池化算力运行大模型，可以试用 Mesh LLM，但需注意其仍处于早期阶段。[2.
