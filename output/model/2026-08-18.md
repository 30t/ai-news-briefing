**Claude 系统提示词文档更新：了解模型“出厂设置”的窗口**

[10. Claude: System Prompts](https://platform.claude.com/docs/en/release-notes/system-prompts) 在 Hacker News 上获得 480 分的高关注。这篇文档公开了 Claude 在网页版（claude.ai）和 iOS/Android 移动端使用的系统提示词（system prompt，即每次对话开始时注入给模型的指令，用于提供当前日期、鼓励 Markdown 格式输出等行为约束）。

**背景**：Claude 的网页和移动端产品在每次对话开始时，会通过一段系统提示词告诉模型“今天是什么日期”“应该用什么格式回答”等信息。这段提示词会定期更新以改善回答质量。

**这次的变化**：Anthropic 公开了这些系统提示词的更新日志，并明确说明这些更新**不适用于 Claude API**——也就是说，开发者通过 API 调用时不会自动获得这些行为调整。从 Claude 4.6 代开始，每个模型 ID 是固定快照，不再随系统提示词变化。

**为什么重要**：对于普通用户，这解释了为什么网页版和 API 的行为可能不同；对于开发者，这提醒你 API 调用需要自己管理提示词和上下文，不能依赖网页端的行为优化。原文未给出量化结果，属于文档公开而非功能更新。

**建议动作**：如果你在用 Claude 网页版做日常任务，可以浏览这份文档了解模型被“预设”了哪些行为；如果你是 API 开发者，不必关注此更新，你的调用不受影响。

## Agent / 编程工具趋势

**Mole 出 Mac 版后的产品反思：AI 时代的三类“垃圾”与清理哲学**

[3. Mole 出 Mac 版后，用户教会了我做产品](https://tw93.fun/2026-08-16/mole-mac.html) 是一篇来自独立开发者 TW93 的深度复盘。Mole 最初是一个开源的 Mac 清理命令行工具（CLI，即终端中运行的命令工具），去年国庆在泳池边写了几百行代码，不到一年收获 60K star、121 位贡献者，解决了近 800 个功能建议和 Bug。后来因为 README 图片流量把 Vercel 账单跑超 80 美元，作者意识到用户量已经很大，于是用两个周末做了 Mac 桌面版，当晚发布后收到来自法国、德国等地的付费订单。

**核心洞察**：作者发现 AI 工具留下的“垃圾”与传统软件完全不同，分为三类：

1. **编译产物**：AI Agent 让编译频率从每天几次暴增到一下午十几轮。Rust 项目的 target、前端的 .next 和 dist、Xcode 的 DerivedData，作者一次清出 86GB。
2. **AI 工具自身的旧版本**：Claude Code、Cursor Agent、GitHub Copilot 等 CLI 工具自动更新时，每个新版本约 250MB 下载到新目录，旧版本不删除，几个月积攒十几个无用版本。
3. **模型文件**：Ollama 和 LM Studio 拉取的模型、HuggingFace 缓存，常常几十 GB。

**关键设计决策**：Mole 将清理对象分为三档——第一档“可再生”（HTTP 缓存、编译产物、日志）默认勾选清理；第二档“重建代价高”（包管理器缓存、本地模型权重）需要用户过目；第三档“不可替代”（聊天记录、邮件库、照片图库、项目状态）绝不放进一键清理列表。作者强调，把三档压成一份“安全可删”清单虽然省事，但代价是替用户做了决定。

**为什么重要**：这篇文章反映了 AI 编程工具普及后的真实副作用——Agent 驱动的开发模式正在改变本地存储的使用模式。对于重度使用 Claude Code、Codex、Cursor 等工具的开发者，理解这三类垃圾的分类逻辑，比盲目清理更安全。

**建议动作**：如果你在用 AI 编程工具，检查一下你的 target、.next、DerivedData 目录和 ~/.cache 下 Claude Code / Cursor 的旧版本目录；清理前先确认哪些是“可重建”的，哪些是“不可替代”的。注意：这是个人开发者经验分享，属于技术社区内容，非官方指南。

## 开源项目 Release 汇总

**llama.cpp b10456：修复 Intel GPU 上的量化拷贝性能瓶颈**

[1. llama.cpp b10456：修复SYCL量化拷贝内核线程/块计数，Arc 70上q4_0到f32吞吐量提升至158 GB/s](https://github.com/ggml-org/llama.cpp/releases/tag/b10456) 是本次唯一的官方确认版本更新。llama.cpp 是当前最流行的本地大模型推理框架（支持在 CPU、GPU 上运行量化后的模型），本次更新针对的是其 SYCL 后端（SYCL 是 Intel 主导的异构计算编程标准，用于在 Intel GPU 上运行计算任务）。

**原来的问题**：在 SYCL 后端的量化拷贝内核（quantized cpy kernel，负责在量化格式和浮点格式之间转换数据的内核）中，线程/块计数没有与量化大小成比例调整，导致 GPU 计算资源过度订阅或不足订阅，性能受限。

**这次的变化**：b10456 调整了线程/块计数逻辑，使其与量化大小成比例。在 Intel Arc 70 GPU 上，q4_0 到 f32 路径（4-bit 量化格式转 32 位浮点格式）的吞吐量从 20.21 GB/s 提升至 158.19 GB/s，提升约 7.8 倍；其他量化路径性能持平。

**为什么重要**：对于使用 Intel Arc GPU 进行本地推理的用户，这个修复可能显著改善特定量化路径的性能。但影响范围有限——只涉及 SYCL 后端和特定量化转换路径，NVIDIA/AMD 用户不受影响。原文未明确说明从哪个版本升级而来，但这是 b10456 版本。

**建议动作**：如果你在用 Intel Arc GPU 跑 llama.cpp，建议升级到 b10456 并测试 q4_0 到 f32 路径的性能；其他用户可暂不关注。

**Qwen 3.8 27B：开源视觉模型能力出色，但默认“过度思考”是硬伤**

[4. Qwen 3.8 27B 发布：Apache 2.0 开源视觉模型，默认过度思考问题引关注](https://simonwillison.net/2026/Aug/16/qwen-38-27b) 是今天最值得关注的开源模型新闻。Simon Willison 在 MacBook Pro（128GB M5 Max）和 NVIDIA DGX Spark 上实测了阿里 Qwen 实验室发布的 Qwen 3.8 27B——一个 Apache 2.0 许可、270 亿参数的视觉能力大语言模型（可以同时理解文本和图像）。

**背景**：27B 参数规模是本地运行的“甜点区”——配置合理的笔记本就能跑。前代 Qwen 3.6 27B 已经表现不错，而 Qwen 官方自报基准显示 3.8 27B 同时超越了前代和闭源的 Qwen 3.7-Plus（后者直到今年 5 月还是 Qwen 最强模型之一）。

**这次的关键发现**：Qwen 3.8 27B 默认的推理强度（reasoning_effort）设置为 xhigh（极高），这导致模型对简单问题也会进行大量“内心独白”。实测中，生成一个鹈鹕骑自行车的 SVG 图像，xhigh 模式耗时 21 分钟、使用 22,276 个推理 token 产出 3,223 个输出 token；关闭推理后同一任务仅需 137 秒。更夸张的是，让模型画一个简单的圆形 SVG，xhigh 模式下模型会自己脑补出“几何圆形研究”“包豪斯配色”等复杂方案。

**具体变化**：Qwen 3.8 官方支持 reasoning_effort 参数，可设为 xhigh（默认，适合复杂任务）、medium（平衡精度和速度）、low（优化速度和成本）。但 LM Studio 的 GGUF 版本保留了 xhigh 默认值，且默认上下文限制 8,192 token 会被 Qwen 轻松耗尽——作者改用完整 262,144 最大上下文后才解决。

**为什么重要**：这个默认值问题直接影响本地部署的效率和成本。模型本身能力很强（作者称这是“用本地机器跑出过的最好的鹈鹕 SVG”），但默认设置会让简单任务耗时膨胀近 10 倍。对于消费级硬件用户，这比模型能力更影响选型决策。

**建议动作**：如果你打算本地部署 Qwen 3.8 27B，务必手动将 reasoning_effort 设为 low 或 medium，并调大上下文窗口。注意：这是 Simon Willison 的个人实测，属于技术社区内容，非官方基准；独立基准测试结果尚未公布。同主题的 [11. Qwen 3.8 27B 表现出色，但默认推理强度过高导致过度思考](https://aihot.virxact.com/items/cmswesk6a0r2hrovml2edcl2c) 为待验证来源，内容与上述一致，不再重复展开。

**SSOG-Attention：用可分离高斯和替代标准注意力，复杂度从 O(N²) 降到 O(N·√N)**

[6. SSOG-Attention: Sum Of Separable Gaussians as a sub-quadratic and scalable alternative to SDPA. 【R】](https://www.reddit.com/r/MachineLearning/comments/1vpt6ay/ssogattention_sum_of_separable_gaussians_as_a) 是 Reddit r/MachineLearning 上的研究分享。标准缩放点积注意力（SDPA，即 Transformer 中计算 token 之间相关性的核心机制）需要计算所有 token 两两之间的相似度，复杂度为 O(N²·d)——当输入序列变长时，计算量呈平方级增长。

**这次的方法**：SSOG（可分离高斯之和）为每个注意力头学习少量“高斯原子”，然后根据查询 token 几何地“引导”这些原子。由于原子可以分解为可分离的高斯和，复杂度降至 O(N·√N·d)。实验显示，在小数据集（CIFAR-100）上 SSOG 明显优于 SDPA，在更大数据集（ImageNet-1k）上性能相当但收敛更快，且随规模增大在速度和内存效率上优势更明显。

**需要提醒**：这是 Reddit 上的研究分享，属于技术社区讨论，不等于官方确认；论文和代码已公开（GitHub 仓库），但这是研究信号，不等于已经产品化。作者也承认部分代码和博客内容使用了 AI 辅助生成。

**建议动作**：对注意力机制优化感兴趣的研究者可以阅读博客和代码；普通读者可暂时忽略，这属于前沿研究范畴。

2. **升级 llama.cpp 到 b10456**：如果你使用 Intel Arc GPU 跑本地推理，升级后测试 q4_0 到 f32 路径的性能，可能有近 8 倍提升；其他 GPU 用户可暂不关注。

3. **清理 AI 工具产生的“垃圾”**：如果你重度使用 Claude Code、Codex、Cursor 等 AI 编程工具，检查 target、.next、DerivedData 目录和 ~/.cache 下的旧版本文件。清理前先分类：可再生（缓存、编译产物）可清，重建代价高（模型权重、包缓存）需过目，不可替代（聊天记录、项目状态）绝不碰。

4. **跟踪 NVIDIA 融资担保缩减**：关注后续官方声明和详细报道，这是 AI 算力投资的重要信号，但不宜过度解读。

5. **暂时忽略 Speko 和 GPT 5.6 Sol 的结论**：Speko 信息不足，GPT 5.6 Sol 的测试基准未公开，均需等待更多验证。

6. **归档 SSOG-Attention 论文**：对注意力机制优化感兴趣的研究者可阅读，普通读者可忽略。
