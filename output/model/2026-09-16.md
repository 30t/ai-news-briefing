## 开源项目 Release 汇总

**Ollama v0.34.1：MLX safetensors 创建转正，GGUF 创建改走 llama.cpp 工具链**

Ollama（本地运行大模型的开源工具，让开发者在自己的电脑上拉取、创建和运行模型）这次发布的是主项目 v0.34.1，原文未明确说明从哪个版本升级而来，但对比链接显示是从 v0.34.0 到 v0.34.1-rc1 的区间。原来的问题是：用 MLX safetensors（Apple 生态的模型权重格式）通过 `ollama create` 创建模型还属于实验性功能，而 GGUF（llama.cpp 生态常用的模型格式）的创建路径和 llama.cpp 工具链存在重叠。这次的具体变化是：MLX safetensors 的 `ollama create` 不再标记为实验性，GGUF 模型创建则改为必须使用 llama.cpp 工具链做 safetensor 转换和量化。此外还改进了 Apple Silicon 上的 MLX 内存处理，把重复 token 检测阈值提高到 100 以减少 OCR 等场景的误报，弃用 `typical_p` 参数（已有 GGUF 模型仍保留支持），并让 `/api/tags` 在大模型库下更快。原文给出的量化结果是：`/api/tags` 冷启动测试从 3.1 秒降到 294 毫秒。为什么重要：如果你有脚本依赖旧的 GGUF 创建流程，或者依赖 `typical_p`，这次会直接影响你；Apple Silicon 用户和模型库较大的用户会感受到性能改善。建议动作：检查现有 `ollama create` 脚本是否走 GGUF 路径，确认是否需要迁移到 llama.cpp 工具链；如果依赖 `/api/tags` 做自动化，可以实测一下提速效果。

**llama.cpp b10985：RPC 后端修复缓存误写，仅对权重张量启用 hash-cache**

llama.cpp（本地大模型推理的底层开源项目，也是 GGUF 格式的来源）这次发布的是主项目的构建版本 b10985，属于日常滚动构建，原文未明确说明从哪个版本升级而来。原来的问题是：RPC 后端（让 llama.cpp 把推理任务拆到多台机器上跑的功能）会把所有超过阈值的数据传输都做哈希并写入 worker 缓存目录，但缓存本来是为权重设计的，激活值（推理过程中间产生的数据）也走了同一条路径。原文给出的证据是：两节点拆分 Qwen3.8-Flash-Next 时，每个超过 10MB 的 prefill ubatch 都被哈希并写入缓存，一天累积达 1.4TB。这次的具体变化是：hash-cache 路径只对标记为权重用途的张量生效，并且只保存未命中哈希检查的那一个张量，同时在 SET_TENSOR 载荷中用 `cache_flag` 替代服务端的 `pending_cache` 状态。为什么重要：对用 llama.cpp RPC 做多节点分布式推理的用户，这是一个影响部署稳定性的实际修复，能避免磁盘被激活值缓存写满。建议动作：如果你在用 RPC 多节点推理，建议升级并检查 worker 缓存目录的历史占用；如果只是单机本地推理，这条优先级不高。

**Hacker News 热帖：称 25 分钟内获取 Baseten 生产 GitHub 管理员权限**

这是一条技术社区讨论，不等于官方确认。Hacker News 上出现一篇标题为“We got admin access to Baseten's production GitHub in 25 minutes”的帖子，获得 203 分，指向 strix.ai 博客中关于 Baseten Harbor GitHub PAT（personal access token，个人访问令牌，相当于访问代码仓库的钥匙）接管的文章。Baseten 是一家提供模型推理服务的公司，原文提到其估值 130 亿美元。文章称，作者用自家安全 Agent Strix 扫描 `*.baseten.co`，在约 25 分钟内从一个公开 Docker 镜像里找到一个仍然有效的 GitHub token，该 token 对 Baseten 主产品仓库、驱动集群的 GitOps 仓库和 Homebrew tap 有管理员和推送权限，镜像构建时间可追溯到 2023 年 3 月，token 在 2026 年 7 月被发现时仍然有效。需要强调的是：候选信息只提供了 HN 分数和博客摘要，没有 Baseten 官方回应、完整攻击路径或修复状态，因此不能当作已确认事实。为什么重要：如果属实，这类 AI 基础设施供应链权限泄露对使用 Baseten 或类似推理平台的团队有安全警示意义。建议动作：暂时把它当作待验证线索归档，关注 Baseten 官方是否回应；同时自查自己的公开镜像和 CI 产物里是否残留长期有效的 token。

**Google 发布 Gemini 3.8 Live 与 3.8 Live Extended Thinking 语音到语音模型**

这是一条技术社区来源，不等于官方确认。据 Simon Willison 博客，Google 当天发布 Gemini 3.8 Live 和 3.8 Live Extended Thinking 两个语音到语音模型（speech-to-speech，指直接处理语音输入并输出语音，而不是先转文字再合成），形态与 OpenAI 的 GPT-Live 系列类似。背景是：实时语音交互一直是 Agent 和客服、助手类产品的关键能力，但过去很多方案是“语音转文字 → 文本模型 → 文字转语音”的拼接流程，延迟和语气损失都比较明显。这次的具体变化是：作者用 GPT-6 Astra Extra High 生成了一个无依赖的浏览器 Web UI，可以选取模型和语音预设、输入系统提示词并开始语音对话，还支持打断模型说话；实现直接连接 Google 的 BidiGenerateContent WebSocket 端点，并用 Web Audio API 做采集和播放。原文没有给出官方规格、价格或 API 可用性细节，也没有量化延迟或质量结果。为什么重要：语音到语音模型直接影响实时 Agent 与语音交互产品的技术选型，如果 Google 正式开放，会改变这一层的竞争格局。建议动作：关注 Google 官方文档和 API 开放状态，先不要基于社区博客做生产选型；如果做语音产品，可以把这类模型列入观察清单。

## 前沿研究观察

**arXiv 论文：Capable but Careless — 电脑操作型 Agent 是否遵守上下文完整性**

这是一篇 arXiv 论文，属于研究信号，不等于已经产品化。研究问题是：电脑操作型 Agent（computer-use agents，指能直接操作浏览器、桌面等界面的 Agent）在完成任务时，是否会遵守上下文完整性（contextual integrity，指信息是否在合适的场景、以合适的方式被使用和传播）。原来的问题是：Agent 能力评测大多关注任务完成率，很少系统检查它在操作过程中是否越界使用或泄露信息。这次论文的具体方法和实验对象，候选信息只提供了摘要页和标题，没有给出实验设计、数据集、结果数字和局限，因此原文信息不足，无法判断具体结论强度。为什么重要：如果电脑操作型 Agent 开始进入企业流程，隐私边界会成为能否上生产的关键门槛。建议动作：把这篇论文加入阅读清单，重点看它的评测方法和失败案例；在自建 Agent 时，提前设计信息访问范围限制，不要只盯任务成功率。

**arXiv 论文提出 PMPA：针对 Claude Code、OpenClaw 等 Harness 型 Agent 的持久记忆投毒攻击**

这是一篇 arXiv 论文，属于研究信号，不等于已经产品化。论文提出 PMPA（Persistent Memory Poisoning Attack，持久记忆投毒攻击），针对的是 Harness 型 Agent（指 Claude Code、OpenClaw 这类带工具调用和持久记忆的 Agent 框架）。原来的问题是：这类 Agent 会把外部信息写入持久记忆，之后在后续会话中检索使用，但很少有人检查这些记忆是否被污染。这次的具体变化是：攻击者把恶意指令嵌入良性外部来源，诱导受害 Agent 在未直接访问攻击者框架的情况下，把恶意指令写入持久记忆，之后在后续会话中被检索并触发恶意行为和隐私泄露。作者在 OpenClaw 和 Claude Code 上跨不同骨干 LLM、输入模态和触发场景做了评测，并测试了一种提示层防御。原文没有给出具体攻击成功率、防御有效率等量化数字，因此原文信息不足，无法判断防御强度。为什么重要：它揭示了 Agent 持久记忆机制可被跨会话利用的攻击面，对使用 Claude Code 等编码 Agent 和自建 Agent 工作流的开发者有直接的安全与隐私警示价值。建议动作：检查你的 Agent 是否有持久记忆写入，是否对外部来源内容做了隔离或审核；把“记忆写入前是否需要人工确认（HITL，人在回路中）”列入设计讨论。
