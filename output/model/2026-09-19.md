## 开源项目 Release 汇总
### Ollama v0.34.3-rc0：本地推理工具开始把“思考强度”变成可读接口
Ollama（本地运行大模型的开源工具，让开发者在自己的机器上跑模型并提供 API）发布了 v0.34.3-rc0。这是一个预发布版本（rc 即 release candidate，候选发布版），更适合开发者测试，不一定适合生产环境；原文未明确说明从哪个版本升级而来，只给出了与 v0.34.2 的对比链接。

原来的问题是：不同模型对“思考强度”这类推理控制项的支持方式不统一，开发者很难在程序里知道某个模型支持哪些档位、默认用哪档。这次 `GET /api/show` 会返回每个模型的 thinking 控制项及默认值，示例中 `glm-5.3-flash:cloud` 返回 `values` 为 low/high/max、`default` 为 max。此外，Nemotron H 视觉模型在 Apple Silicon 上通过 MLX（苹果的机器学习框架，用于在 Mac 芯片上高效推理）获得支持，macOS 应用不再重新打开已关闭的窗口。

原文未给出明确量化结果。为什么值得关注：对通过 Ollama API 构建 Agent 或本地推理流程的开发者，thinking 控制项可被程序化读取，有助于按模型能力动态调整推理策略。建议动作：如果你在用 Ollama 做多模型路由，可以先在测试环境验证 `/api/show` 的返回结构，再决定是否接入生产逻辑。

### OpenHands v1.19.0：把 Agent 配置绑定到特定 MCP 服务器
OpenHands（一个开源的 AI 编程 Agent 平台，可以自动完成代码修改、运行命令等任务）发布 v1.19.0，原文未明确说明从哪个版本升级而来。

这次更新的关键变化包括：支持把某个 agent profile（Agent 配置档案）作用域限定到特定的 MCP 服务器（MCP 是让 Agent 连接外部工具和数据源的协议）；新增 GPT-6 Astra 模型支持；在 UI 中展示自动化被禁用的原因；以及一批 bug 修复，例如识别 Azure DevOps 的 SSH 远程地址、避免重复拉取自动化 SDK 版本、把客户端 ACP 注册表固定到 agent-server 并移除 codex shim 等。

原文未给出明确量化结果。为什么值得关注：把 Agent 配置和 MCP 服务器绑定，意味着团队可以更精细地控制“哪个 Agent 能用哪些工具”，这是 Agent 安全与权限治理的一步。建议动作：如果你在用 OpenHands 接多个 MCP 工具，值得检查新版本的作用域配置方式，评估是否能减少工具越权风险。

### CrewAI 1.15.22：多模型路由与平台集成继续补齐
CrewAI（一个构建多 Agent 协作工作流的开源框架）发布 1.15.22，原文未明确说明从哪个版本升级而来。

本次 Features 包括：支持用别名作为连接标识；记录部署创建失败的原因；在 tracing（追踪，用于观察 Agent 执行过程）中收集人类反馈和暂停事件；新增 `llm_overlay` 上下文变量，用于把不同 agent 角色路由到不同模型；在 agent 执行负载中携带 `task_prompt` 和输出；在 crew 设置阶段校验平台集成；把平台工具加入 JSON crew 向导；暴露 CrewAI Platform 应用目录；新增 OpenRouter 作为支持的 embedding（向量化）提供商。Bug 修复覆盖 CRLF 技能定义、SQLite 连接关闭、Gemini 文件内容保留、向 OpenAI 推理模型发送 `reasoning_effort` 等。

原文未给出明确量化结果。为什么值得关注：`llm_overlay` 这类按角色路由模型的能力，直接影响多 Agent 系统的成本和效果平衡。建议动作：如果你在用 CrewAI 做多 Agent 编排，可以关注 `llm_overlay` 是否适合你的成本优化场景，但升级前建议先在测试环境验证。

## 企业应用 / 商业化信号
### GitHub Actions 执行保护正式 GA：自动化流水线的“谁能触发”有了官方开关
GitHub Actions（GitHub 的 CI/CD 自动化服务，用于在代码提交后自动构建、测试、部署）的工作流执行保护，此前处于公开预览，现在正式 GA（generally available，正式可用），覆盖 GitHub Enterprise、组织和仓库层级。

原来的问题是：工作流一旦配置好，触发权限往往比较粗放，容易出现误触发或供应链风险。这次执行保护允许定义允许列表（allowlist），控制谁可以触发工作流、哪些事件可以启动它——actor 规则管“谁”，event 规则管“什么事件”，两者在运行前一起评估。

GA 相比预览新增了三项能力：工作流文件定向（把规则限定到具体 workflow 文件，比如只限制 deploy.yml 给指定团队，而 CI 对所有贡献者开放）；Insights（查看规则在企业、组织、仓库层面的评估和执行情况，便于审计和调优）；REST API（以代码方式管理执行保护规则，支持增删改查，便于在数百个仓库间保持一致并接入现有治理工具）。

原文未给出明确量化结果。为什么值得关注：对依赖 GitHub Actions 运行自动化与 Agent 工作流的团队，执行保护 GA 意味着可以用官方机制收紧触发权限，降低供应链与误触发风险。建议动作：检查你组织里高风险 workflow（尤其是部署类）是否已配置 actor 和 event 规则，并评估是否用 REST API 把策略纳入代码化管理。

### Copilot 预算申请 GA：AI 额度用完不再直接“断供”
GitHub 的 Copilot 预算增加申请功能正式 GA。原来的问题是：当成员用完了可用的 Copilot AI credits（AI 额度），就会被直接挡在消耗额度的 Copilot 功能之外，没有顺畅的申请通道。

这次新增了一个流程：成员在触达上限的当下就可以申请更多预算；组织所有者、企业所有者或账单管理员可以在设置里直接批准、调整或拒绝，无需离开当前界面。申请会自动路由到实际支付该预算的账户——组织拥有的预算出现在组织设置，企业拥有的预算出现在企业设置。批准后，成员预算更新为你设定的金额，并立即恢复 AI credits 访问。

该功能适用于 GitHub Copilot Business 和 GitHub Copilot Enterprise 计划下的按用量计费，不适用于使用 managed users 的企业。原文未给出明确量化结果。为什么值得关注：这说明 AI 编程工具的“成本治理”正在从后台账单问题变成产品内流程，对团队预算管理和开发者体验都有影响。建议动作：如果你是组织或企业管理员，可以检查当前 Copilot 预算设置，决定是否开放成员自助申请通道。

### GitHub Copilot 周报（9月14日）：模型选择分档与 Sentry 集成
GitHub 发布 Copilot 9月14日当周更新，属于渐进式周报，原文未展开各项改动的具体细节。

主要变化包括：Copilot 代码审查现在会在后续审查中解决已处理的评论，保留未解决反馈；在应用代码建议时建议提交信息；审查可以使用 shell 工具验证改动；Lite 审查现在会合并多个 agent 的发现。自动模型选择新增 efficiency、balance、intelligence 三档，让用户选择 Copilot 如何在成本、质量和响应时间之间权衡，三档从同一批可用模型中选择，该更新正在 VS Code、Copilot CLI 和 Copilot 应用中逐步推出。此外还有面向管理员的 VS Code Agents 窗口使用指标 GA、仓库自定义属性值建议的公开预览，以及 Copilot 预算申请入口。

原文未给出明确量化结果。为什么值得关注：模型选择分档把“成本 vs 质量”的权衡显式交给用户，Sentry 集成则把错误排查纳入 Copilot 应用。建议动作：如果你在用 Copilot，可以试用三档模型选择，观察不同档位在你日常任务上的实际差异。

### TabPFN-3.5：表格数据基础模型的社区发布信号
这是一条来自 Reddit r/MachineLearning 的社区讨论，不等于官方确认，结果可能受测试条件、样本和硬件环境影响。

TabPFN（面向表格数据的预训练基础模型，主打在小到中等规模表格任务上少调参、快速出结果）由 Prior Labs 发布 3.5 版本。据帖子描述，该模型在 TabArena 和 BeyondArena 两个评测榜上排名靠前，支持 100 万行、最多 2 万特征。它包含三个变体：TabPFN-3.5-Fast（alpha 阶段，比基础模型快 6 倍）、TabPFN-3.5-Thinking（通过 API 用更多计算换更高准确率）、TabPFN-3.5-Plus。

帖子称，在 BeyondArena 上，TabPFN-3.5 在文本丰富、高基数和高维数据上领先，比此前最强基线高 250 Elo 分，比此前总榜领先者高 150 Elo 分；TabPFN-3.5-Thinking 在 BeyondArena 上比基础模型高 20 Elo，在 TabArena 上高 44 Elo。这些数字来自社区帖子，未经独立验证。为什么值得关注：表格数据是很多企业真实业务的载体，如果该模型能力属实，可能影响结构化数据场景的建模方式。建议动作：先把它当作早期线索归档，若你有表格预测任务，可在小数据集上自行验证，不要直接据此做采购决策。

### 被污染的 benchmark 可能影响自我修改型编程 Agent
这是一篇 arXiv 论文，属于早期研究信号，不等于已经产品化。原文摘要信息有限，以下基于标题和摘要页可见内容解读。

研究问题：编程 Agent 如果具备自我修改能力，它的行为可能被训练或评测所用的 benchmark（标准化评测集）所影响。论文标题“Reflections on Trusting Trust, Revisited”呼应了经典的“信任信任”安全问题，暗示供应链式的污染风险——如果 benchmark 本身被投毒，Agent 可能学到错误行为。

方法方向：用被污染的 benchmark 去影响自我修改型 AI 编程 Agent。原文摘要页未给出具体实验对象、结果数字和局限，原文信息不足，无法判断具体方法细节和量化结论。

为什么重要：如果编程 Agent 会依据评测反馈自我调整，那么评测数据的可信度就直接关系到 Agent 的行为安全。这提醒我们，Agent 能力分数不等于真实工程能力，评测链路本身也需要被审计。建议动作：把这篇论文作为风险线索归档，关注后续是否有可复现的实验细节；在内部使用 Agent 评测时，注意评测集来源和污染风险。
